# Team chat message

**Job.** Move exactly one thing forward — get an answer, correct a premise, hand over a
finding, ask for a confirmation.

## Settle before drafting

- **Who**, and whether this opens a thread or continues one.
- **The single ask.** If there are two, say so and check whether it should be two messages.
- **The stance** — asking, informing, or disagreeing. If disagreeing, how firmly. Never pick
  this for the author.
- **What the reader can already see** — the screenshot, the ticket, the previous message.
- **Whether anyone else is on the thread**, and whether they are the real audience.

## Rules

- Open with `Hi <name>` or `Hello <name>`. Drop the greeting when continuing an active thread.
- **No email structures.** No "Hope you are doing well", no "Thanking you", no sign-off, no
  signature, no name at the end.
- A few short lines. No headings, and **no bullet lists unless genuinely enumerating options**
  — this overrides the bullets-by-default rule in `SKILL.md`. Prose is right here.
- **Assert the conclusion.** The maths, the estimates and the code path that convinced the
  author stay in the conversation; the message carries the claim.
- Point at what the reader can already see rather than re-explaining it.
- Say "we" for team decisions, "I" for the author's own actions.
- A message that asks for something also says what the author will do next.

## Channel constraints

A chat client renders markdown poorly — headings, tables and heavy bold do not survive. If the
content needs more than a few lines, raise that it probably belongs in a document with the
message pointing at it.

## Failure modes specific to this type

- **Taking a position on a contested point on the author's behalf.** Confirm the position, and
  how hard to hold it, before writing it into something they will send.
- **Stating something from memory or another project as established fact.** Everything in a
  message the author sends is something they are personally vouching for.
